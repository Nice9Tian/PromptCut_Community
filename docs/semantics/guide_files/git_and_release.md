# 提交与发版

索引见 `../README.md`。

## 提交

- 提交信息用中文，开头写类别，冒号后写做了什么。常用类别：文档、探针、重构、修、测试、合并。
- 分支合并进 main 用 `--no-ff`（在 GitHub 上合 PR 时选 "Create a merge commit"），合并提交写成「合并 <分支或步骤名>:摘要」。
- 提交 PR 之前自己先过一遍，三项都要：`npm run build` 成功；这次改动影响范围内的测试零失败；本次改到的功能，其对应探针通过，结果写成一个文件附在 PR 里（范围怎么算、探针结果怎么写见 `verification.md`）。不推进 `release`，`release` 只在发版时动。

## release 分支

- `release` 指向最近一次正式发布的版本：它永远能构建、能运行、能使用。main 是日常合入的地方，功能随时往里合；`release` 不跟着动。
- **时机：只在发版时推进一次。** 发版时 `git checkout release && git merge --ff-only main`，之后 main 继续前进，`release` 留在原地等下一次发版。`release` 只从 main 前进，不直接提交，不改写历史。
- 合入条件，四条同时满足：类型检查零错误；**全量 `npm test` 零失败**（`verification.md`，这是全量唯一一次必跑的时机）；整套验收跑过（G0 通用门槛、G0-R 渲染附加项，项目与标准见 `../../plan/Master-Execution-Plan.md` 第 8 节；加全部历史探针）；`npm run build` 成功，改动涉及桌面壳、Chrome、ffmpeg、内置 Python 或运行时目录布局时，`desktop/` 下的发版构建也成功。
- 合入 main 的门槛不跑全量测试、也不跑整套历史探针，见 `verification.md`「PR、main、release 分别验什么」：在**合并后的状态**上把上面那三项（`npm run build`、受影响范围的测试、对应探针）跑过即可；改到画面的改动再加渲染附加项（G0-R）。

## 构建

- 先提交，再构建。构建产物必须对应一个已提交的版本，不能对应工作区状态。
- 网页构建：`npm run build`（先类型检查，再 `vite build`）。
- 桌面发版：在 `desktop/` 下运行 `npm run release -- --from-head`，源码取自 HEAD。

## 版本号

版本号只在发版时改，不是每次合并都改。

两个版本号分开：

- **应用版本**：根目录 `package.json`，对应 Node 那一半，更新补丁负责更新它。
- **外壳版本**：`desktop/src-tauri/tauri.conf.json`，对应 Rust 外壳、Chrome、ffmpeg、内置 Python，只随完整安装包更新。

格式都是 `0.<内核代次>.<修订>`。改完先问：Node 这一半放到老外壳上，还能不能照常跑？判断时不看改的是不是 Rust，看缺了新外壳会不会出事：加一个菜单项、多一个可选入口，都属于下表第二行。

| 情况 | 怎么进位 | 用户怎么升级 |
|---|---|---|
| 只动了 Node 那一半 | 应用版本末位 +1 | 更新补丁 |
| 动了 Rust，但老外壳上能降级运行 | 应用版本末位 +1，外壳版本末位 +1 | 更新补丁 |
| Node 那一半有大规模业务重构，值得升应用中间位，但老外壳上照常能跑 | 应用版本中间位 +1、末位归零，外壳版本只动末位（没改 Rust 就不动） | 更新补丁 |
| 动了 Rust 且 Node 硬依赖它；换了 Chrome、ffmpeg、内置 Python；运行时目录布局变了 | 两个版本号的中间位一起 +1 | 完整安装包 |

应用版本的中间位可以单独进位，不必拖着外壳一起换代。补丁能不能装只看外壳代次（见下文 `shellGeneration`），不看应用版本，所以只要外壳保持向后兼容，就强烈建议外壳只动末位、不升中间位（如 `0.2.x` → `0.2.x+1`）。这样老用户仍能收到只含代码层的更新补丁热更新，不必重新下载完整安装包。先例：0.6.0 把应用从 0.5.x 升到 0.6.0（T1–T5 重构），外壳只从 0.2.5 升到 0.2.6，老用户用约 7 MB 的补丁完成升级，没有下载约 400 MB 的完整安装包。

补丁清单用两个字段拦住装不上的用户：

- `shellGeneration`（外壳版本的前两段，如 `0.2`）：代次不同直接拒绝。
- `minShellVersion`（`desktop/scripts/make-patch.mjs` 顶部手写的常量）：代次相同但外壳比它旧，也拒绝。它只在第三种情况下抬高，回答的是「Node 这一半最低需要什么外壳」，不是「这次顺手编了什么外壳」。外壳换代时要把它挪到新代次的起点。
